## 1. The auth rework (the release's reason to exist)

Nine ways to be trusted become three. Full argument in `project_zimi_auth_simplification` memory; the short version:

| today | 1.10 |
|---|---|
| admin password (file), admin password (env), API token, setup key, `lan_admin`, accounts + sessions, secondary-admin role, SSO header, access modes | accounts, roles, one bootstrap secret |

**One bootstrap door.** Always the setup key, no loopback exception. This is the change that actually retires loopback-as-proof, and with it the residual documented in `_is_loopback_client`: a same-host forwarder that sends no forwarded header (`socat`, `proxy_pass` with no `proxy_set_header`) still presents as the host today, and no amount of header inspection can tell it from the owner at the keyboard.

**Every credential belongs to an account.** The API token becomes a token *on* an account rather than a parallel god-mode. SSO creates an account. "Open" becomes an explicit anonymous account carrying a role, not the absence of a check.

**Network position stops being a credential.** It becomes policy on the anonymous role. `lan_admin` already *is* that, expressed as a branch inside the auth check instead of as configuration.

**Known cost:** the desktop app currently gets admin by being on the host. Under one door it must fetch the key from the data dir itself. That is the piece of work that makes this a release rather than a patch, and it needs designing before anything is written.

## 3. Feature B: folders that move files

Also in that document. One constraint discovered since it was written, from the Windows work: **moving a ZIM the server has open fails on Windows.** The move must release the pooled handles first, exactly as the delete route and the auto-updater now do via `server.release_zim_handles`. On POSIX this changes nothing; on Windows it is the difference between working and not.
