# The creation flow, first class — spec

Eric, 2026-09-03: "Use the creation flow more through browser, try all flows, find all UI UX perf and output / display issues on 20 sites including zims released we can compare against for size and coherence and make this first class. The best creation flow anywhere, using the same tools under the hood." And: "All before the cut. We just aren't there yet. This is a big push to try and get there. Jony knows what we need."

## Goal

A person pastes an address and gets a ZIM that is coherent, right-sized, and arrives without babysitting. Measured against Kiwix's own zimit output on the same sites, and against what the person sees on a phone.

Done means: every row of the survey report is green or explained, the compare set is within reason of the released ZIMs on size and beats or matches them on coherence, the create page has been through a design review and the cuts are made, and the phone-path gate passes on prod. Then the tag.

## Parts

### 1. The survey instrument

`scripts/creation-survey.py`. Runs on a Mac with a working Chromium, against a local `zimi serve` on a scratch library, through the real manage API. Playwright drives the actual create page for one job per mode so the UI is measured, not assumed.

Per job it records:

- **flow**: time to first progress line; the longest gap with no new line; any counter that decreased; the completion card's size against the written file; whether cancel stops the job and leaves nothing behind.
- **output**: entries and mimetype breakdown from the ZIM; bytes on disk; text length of the main page; images painted after a full scroll at 390 px; leaked markup in rendered text; console errors; load time; two screenshots (top, and one screen down).
- **compare**: for sites with a released ZIM, the same output measurements on the released file's main page and three random articles, so the report has size per page and coherence side by side.

Output: `docs/plans/2026-09-03-creation-survey.md` (one row per site and engine, sortable) and `scratchpad/survey/<site>/<engine>/*.png`. The report is regenerated by rerunning; it is never hand-edited.

### 2. The matrix

| kind | sites |
|---|---|
| released zimit ZIM exists | solar.lowtechmagazine.com, peps.python.org, planetmath.org, cheatography.com, foss.cooking, sh1.org |
| static docs and blogs | sqlite.org, sive.rs, paulgraham.com, docs.docker.com, react.dev |
| JS-heavy and news | cnn.com, bbc.com, theverge.com, apple.com, github.com/openzim/zimit |
| awkward shapes | news.ycombinator.com, xkcd.com, en.wikipedia.org/wiki/Water_purification, a medium.com article |

Flows: Fast, Rendered, Alive as one page on every site (60 jobs). Whole site, 25 pages, on the six comparison sites with Fast and Rendered (12). Video mode on two short YouTube playlists (2). One bookmark export. Roughly 75 jobs.

### 3. Fixes by evidence

Every defect the report shows becomes a failing test, then a fix, then one commit, ordered by how early a person would hit it. Nothing is fixed without a row in the report that shows it.

### 4. The design pass

After the fixes, the create page goes through the jony-ive-review skill: what to cut, what the running-job screen should feel like, what the completion moment is. The findings are applied before the tag, in commits small enough to read.

### 5. The gate

`scripts/validate-on-prod.py` after the deploy, then Eric on the phone with sqlite.org and a blog. Then the tag.

## Not in scope

New engines. New modes. A community index. Anything that changes the ZIM format.
