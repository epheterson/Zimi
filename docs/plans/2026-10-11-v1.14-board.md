## 1. Where each feature comes from (`zimi/runtimes.py`)

#113 happened because voices worked in Docker and the desktop app and dead-ended on `pip install zimi`, and nothing noticed. One table, one test, one CI job.

- `RUNTIMES`: every optional feature (voices, BitTorrent, rendered capture, alive capture, SingleFile, site crawl (zimit), video, Reddot, WARC import, PDF, MCP) x every install kind (docker, desktop, pip) -> how it arrives there: `bundled`, `sets_up` (Zimi installs it on first use), `extra` (`pip install "zimi[x]"`), `command` (a named setup command), `external` (operator installs a tool), `absent` (not offered; reason).
- `install_kind()`: docker / desktop / pip, from facts already used (frozen, the image's marker).
- `zimi doctor`: the table for this install, with what is ready now. `--check` exits non-zero when a feature declared `bundled` for this kind is not ready.
- Test: every feature has a row for every kind, every non-`bundled` row names how to get it, and the pyproject extras named exist.
- CI: `pip-clean` job installs the built wheel into a bare venv and runs `zimi doctor --check`.

## 2. Turning the password off

The third answer to Who can change settings, under the two switches that exist. Turning Require password off while Reachable from outside is on now offers it instead of refusing.

- Enabling takes a checkbox that spells out the cost ("Anyone who can reach this address can change every setting and delete ZIMs. Accounts stop limiting anything.") and the current password when one exists.
- Stored as `manage_open` in the app prefs. `manage_open()` reads `ZIMI_MANAGE_OPEN` first; when the env var is set it wins and the switch is locked.
- Never purges: the password hash, API token, accounts and sessions stay. Turning it off returns to the password that was there.
- While it is on: a banner at the top of Settings; captures of private addresses are refused unless the operator set `ZIMI_MANAGE_OPEN` themselves; the qBittorrent connection (below) can only come from the environment, or anyone could point Zimi's requests at the operator's network.
- Startup log warning already exists; it now names the Settings switch too.

## 3. External qBittorrent, the *arr way

Issue #53 (L3tum: qBittorrent behind a VPN; CGNAT means mirroring only works through it). The *arr stack's download-client model is what people already have configured:

- Settings > BitTorrent > Engine: Built in / qBittorrent. Fields: URL, username, password (blank when the client bypasses auth for local addresses), category (default `zimi`), path mappings (`qBittorrent path` -> `Zimi path`, one per line). Test button. Env (as shipped): `ZIMI_BT_CLIENT`, `ZIMI_BT_CLIENT_URL`, `ZIMI_BT_CLIENT_USER`, `ZIMI_BT_CLIENT_PASSWORD`, `ZIMI_BT_CLIENT_CATEGORY`, `ZIMI_BT_CLIENT_PATHS` (`remote=local;...`).
- `QBittorrentBackend(BTBackend)` over Web API v2 (stdlib urllib, SID cookie, re-login on 403). Torrents go in with the category and the `.torrent` uploaded (so the info hash is known and qBittorrent needs no route to Kiwix). v5 `start/stop` with v4 `resume/pause` fallback.
- Paths, as Sonarr: Zimi asks qBittorrent to save where a mapping says it can see; otherwise the category's own folder. When done, the content path is mapped back and libzim validates the file, then it is installed: moved by qBittorrent itself (`setLocation`) when the library is mapped, so it keeps seeding with no copy; else hardlinked; else copied while qBittorrent keeps seeding its own.
- Seeding: ratio caps and mirror mode work through the same ledger (list_managed reports mapped paths). Seeding a library file needs the library mapped; without it the seed row says so. Rate limits and connection caps are qBittorrent's own; Zimi does not touch them.
- Safety: Zimi only ever lists, changes or deletes torrents in its category. Delete-with-files is refused for anything whose mapped path is in the library, as the built-in engine already refuses.
- Engine-specific settings (port, UPnP, DHT, connections, rate limits) hide when qBittorrent is the engine.

Proof: a fake qBittorrent server in the suite (login, add, info, delete, setLocation, categories), and a real download against the NAS qBittorrent (v5.2.3, behind gluetun, local bypass on) with the zim-reader container given `/volume1/downloads` at `/downloads`.

## 5. Transmission, and switching engines (Eric, 18:49)

"I love transmission add that at least. Stopped seeds can be purged and honestly maybe we need to handle the like transition between the two? Back and forth? Current and completed?"

Shape: one external-client engine, two API adapters.

- `zimi/btclient.py`: the client-independent half of what `qbittorrent.py` holds today. Config (env or prefs), path mappings, probe, and `ExternalBackend(BTBackend)`: add (upload the .torrent, hash known), payload path, install (client moves into a mapped library, else hardlink, else copy), remove guard (only its category or label; never delete library files), status and list_managed from one normalized row.
- `qbittorrent.py` shrinks to the Web API v2 adapter. `transmission.py`: the RPC adapter (session id on 409, Basic auth, labels as the category, Transmission 3.00+ for labels, `torrent-set-location` with move).
- Settings and env are generic, since nothing has shipped: `ZIMI_BT_CLIENT` (`qbittorrent` | `transmission`), `ZIMI_BT_CLIENT_URL/_USER/_PASSWORD/_CATEGORY/_PATHS`; prefs `bt_client*`; `POST /manage/bt-client`. Engine selector: Built in | qBittorrent | Transmission.

Switching engines (back and forth, current and completed):

- One path, `p2p.switch_engine()`: the old engine goes not-alive first, so running downloads see it and ask for the new engine instead of falling back to HTTP; then it hands its torrents over; then the new one starts.
- Current downloads restart on the new engine. A restart of the same client (mappings edited, port changed) picks the same torrent up where it was, since both keep it.
- Completed: the seed ledger is engine-independent intent. The new engine re-seeds what it can from the ledger; an external client that cannot see the library leaves those intents waiting (one log line names the mapping to add). Seeds come back if you switch back or map the library.
- Handover cleanup: leaving the built-in engine removes its torrents and resume files and the staging partials (the purge). Leaving an external client removes Zimi's torrents from its category: in-flight ones with their partial files, finished ones without touching library files; a client-side copy of a file the library already has goes too.
- Seed accounting covers an external client's own copies (outside the library), so the ratio cap applies to them as it does to library seeds.
- Prod: compose moves to `ZIMI_BT_CLIENT=qbittorrent`, `ZIMI_BT_CLIENT_URL`, `ZIMI_BT_CLIENT_PATHS`.

Proof: a fake Transmission RPC server (the qBittorrent fake's twin), switch tests (download continues on the new engine; seeds re-added; built-in leftovers purged), and a real Transmission container on the NAS for one download.
